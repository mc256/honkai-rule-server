# Phase 0 Research: Ascending Priority Sort

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-05-01

## Decisions

### D1. Scope of the sort flip: rule sort only, not proxy/group collision sort

**Decision**: Reverse only the comparator inside `MergeUnifiedRules` (`internal/merge/rules.go:80-84`). Leave `sortSourcesByPriority` (`internal/merge/pipeline.go:293-307`) and all downstream proxy/group collision-resolution behavior at descending order, unchanged.

**Rationale**: The two sorts serve fundamentally different semantic domains:

- **Rule sort (in `MergeUnifiedRules`)**: governs the order in which rules appear in the served `rules:` block. Mihomo / Clash evaluate rules top-to-bottom and the first matching rule wins. Flipping this to ascending makes "lower priority number = matches first" — which is the operator's intuition (matches `nice` values, priority queue / min-heap).

- **Proxy/group collision sort (in `sortSourcesByPriority`)**: governs the order of source iteration when extracting proxies and groups, which determines the *winner* on a name collision (per feature 002's documented behavior: higher-priority source's proxy keeps the unprefixed name; lower-priority source's gets the per-source prefix). This semantic is independent of routing precedence and is well-established by feature 002.

The user's request explicitly references rule routing precedence (`alpha` priority 1000 vs. custom rule priority 200, lower wins). Nothing in the request implies operators want to invert proxy collision tie-breaks. Conservatively, we do not flip the second sort.

**Alternatives considered**:

- *Flip both sorts in one feature*: rejected. Conflates two semantic domains. If operators have built mental models around feature 002's collision behavior, silently inverting it would be a much larger blast radius than the user requested.
- *Make the sort direction configurable via env var*: rejected. Operator confusion (two sort directions, two configurations) outweighs any flexibility benefit. Pick one direction that matches operator intuition and ship it.

### D2. MATCH fallback handling under ascending sort

**Decision**: No change required. MATCH is appended to the rules slice *after* the contributor sort completes (`rules.go:104-107`); its priority value (`0`) is metadata for the output adapter, not a sort key.

**Rationale**: The current implementation sorts `contributors []contributor`, then appends MATCH separately. Whether the comparator is ascending or descending, MATCH lands at index `len(rules) - 1` either way. This was a deliberate design choice in feature 005 (research D7), which keeps paying dividends here.

If MATCH had been included in the contributor list with priority 0:
- Under descending sort: priority 0 < every operator priority → MATCH sorts last (correct).
- Under ascending sort: priority 0 < every operator priority → MATCH sorts FIRST (wrong).

The current implementation sidesteps both cases by separating concerns. No code change.

**Alternatives considered**:

- *Move MATCH to be priority `MaxInt`*: rejected. Adds a magic number and changes nothing useful — the append-after-sort approach already works.
- *Make the sort key `(IsMATCH ? +∞ : Priority, Name)`*: rejected. Same comment.

### D3. Tie-break direction: alphabetical ascending (unchanged)

**Decision**: Within a priority bucket, contributors continue to sort alphabetically by name in ascending order (`a < b < c`).

**Rationale**: The user's request was about priority *direction*. They did not mention name tie-break, and feature 005's FR-003 already established alphabetical ascending. Continuing this:
1. Matches operator intuition for sort orderings (alphabetical = a-z).
2. Matches the deterministic order shown in priority-bucket header comments (which list names alphabetically).
3. Preserves SC-003 from feature 005 (operator can identify the contributor of any rule by reading the file alone).

If this is also wrong from the operator's perspective, it can be addressed in a follow-up feature; the current change is scoped and reversible.

### D4. Independence from feature 006

**Decision**: Features 006 (emoji literal preservation) and 007 (ascending sort) are independent. Either can land first; they do not interfere.

**Rationale**: 006 touches `internal/output/subscription_mode.go` (a byte-level post-encode transform). 007 touches `internal/merge/rules.go` (the sort comparator inside `MergeUnifiedRules`). Different files, different layers, different test surfaces. No shared lines, no shared abstractions.

When both are merged to master:
- 006 changes the byte representation of supplementary-plane characters in the output (escape → literal).
- 007 changes the order of rule blocks within the `rules:` sequence.

Neither change interacts with the other. The integration snapshot regenerated by 007 will still contain the unchanged `\Uxxxxxxxx` escapes (because 006 hasn't merged yet on the 007 branch); the integration snapshot regenerated by 006 will still contain descending order (because 007 hasn't merged yet on the 006 branch). Once both merge to master, a follow-up snapshot regeneration captures both effects together.

### D5. No call sites depend on the current descending order beyond the listed tests

**Decision**: The grep audit identified six locations referencing the rule-sort comparator output:
- `internal/merge/rules.go` (the comparator itself)
- `internal/merge/rules_test.go` (TC-U-MERGE-UNIFIED-01..06; covered by Phase 3)
- `internal/integration/pipeline_test.go` (TestI_005_01, TestI_005_02, TestI_003_01; covered by Phase 3)
- `internal/integration/testdata/snapshots/served-config.snap.yaml` (regenerated in Phase 4)
- `internal/output/subscription_mode.go`'s `normalizeRulesPriorityComments` (reads priorities/contributors slices in sequence; **order-agnostic** — works correctly under either direction)
- `cmd/server/main.go` (no priority logic)

**Rationale**: No production code branches on whether priority A < B or A > B. The merge layer outputs ordered slices; the output adapter walks them in sequence; the tests assert specific values at specific positions. The blast radius of the comparator flip is fully contained in the listed test files plus the snapshot.
