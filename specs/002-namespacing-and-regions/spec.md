# Feature Specification: Provider Namespacing & Region Grouping (with Trailing-Rule Drop)

**Feature Branch**: `002-namespacing-and-regions`  
**Created**: 2026-04-30  
**Status**: Draft  
**Input**: User description: "Prefix every node, proxy-group, and rule target with the source's `name` so two providers can never collide; require the source `name` to be lowercase ASCII letters only (warn + skip otherwise); group nodes into ISO 3166-1 alpha-2 region groups inferred from the node's display name (Chinese / English / emoji-flag) via a maintained translation table; drop the trailing rule from each upstream's rule list (the usual `MATCH,auto` that would otherwise short-circuit a multi-source merge)."

## Clarifications

### Session 2026-04-30

- Q: Should the operator's own-proxies and own-proxy-groups be visually tagged in the merged output the same way upstream contributions are tagged with their source-name prefix? → A: Yes — every own-proxy and every own-proxy-group MUST be rewritten with a leading single-underscore prefix (`_<original-name>`). The server-emitted region groups MUST follow the same convention as own-groups and use the form `_region_<CC>` (single leading underscore, then the literal `region_`, then the uppercase ISO 3166-1 alpha-2 code). Rationale: a leading `_` is the operator's convention for "added by us, not from any upstream" — visually distinct from upstream-prefixed names (which always start with a lowercase letter per FR-001's `^[a-z]+$` rule on source names) AND distinct from built-in identifiers (DIRECT/REJECT/REJECT-DROP/PASS, which are uppercase). The convention extends to region groups because they are derived/server-emitted, not from any single upstream.
- Q: Do own-proxies participate in `_region_<CC>` group membership when their display name carries a country indicator? → A: No — region grouping operates exclusively on the **upstream-sourced** proxy pool (FR-004's `<provider>_<original>` names). Own-proxies (FR-007a's `_<original>` names) MUST NOT be added to any `_region_*` group regardless of their display-name content. Rationale: own-proxies are the operator's own infrastructure declared explicitly per server; the operator addresses them directly through underscore-prefixed own-groups (FR-007b) rather than through derived region collections. Region groups stay scoped to the "any exit from this country across all my providers" UX they were designed for.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Provider-Prefixed Namespacing Across Proxies, Groups, and Rule Targets (Priority: P1)

When the server merges multiple upstream subscriptions, every proxy, every proxy-group, and every rule target that came from a particular upstream is rewritten with a `<provider>_` prefix. So if the operator has two providers named `alpha` and `beta`, every node, every group, and every rule from each provider becomes immediately identifiable in the merged config — `alpha_Node1`, `beta_Auto`, `RULE-SET,foo,alpha_Proxy` — and there is no possibility of name collision (the per-source-suffix collision strategy from 001's FR-002 is replaced by this stronger always-prefix invariant).

**Why this priority**: Without prefix-namespacing, identifying which provider's exit you're routing through requires inspecting upstream YAML; with it, the client UI immediately tells you. It is also a precondition for everything else in this feature — region groups would otherwise produce ambiguous group names, and trailing-rule-drop's value depends on rule targets already being unambiguous.

**Independent Test**: Configure two upstreams with overlapping proxy names and overlapping group names; fetch the merged subscription; assert every merged proxy name, every merged group name, and every rule target that resolves to a non-built-in (i.e., not DIRECT/REJECT/REJECT-DROP/PASS) name is exactly `<provider>_<original>`. Assert that an upstream group whose `proxies:` list references other proxies/groups by name has every such reference rewritten to its prefixed form.

**Acceptance Scenarios**:

1. **Given** two upstreams `alpha` and `beta`, both contribute a proxy literally named `Node1`, **When** the merge runs, **Then** the served config contains both `alpha_Node1` and `beta_Node1`, and the per-source-suffix collision strategy from 001's FR-002 is not invoked because no collision is possible after prefixing.
2. **Given** an upstream `alpha` declares a group `Auto` whose `proxies:` list references `Node1` and `Node2`, **When** the merge runs, **Then** the served config contains a group `alpha_Auto` whose member list is `[alpha_Node1, alpha_Node2]`.
3. **Given** an upstream `beta` declares a rule `DOMAIN-SUFFIX,example.com,Auto`, **When** the merge runs, **Then** the served config contains the rule `DOMAIN-SUFFIX,example.com,beta_Auto`.
4. **Given** an upstream rule `DOMAIN,a.test,DIRECT` or `MATCH,REJECT`, **When** prefixing is applied, **Then** the rule's target stays `DIRECT` / `REJECT` (built-ins are never prefixed).
5. **Given** a subscriptions CSV row whose `name` is `Alpha_2024` (uppercase + underscore), **When** the server loads the CSV, **Then** the row is excluded from the merged output, a stdout warning identifies the offending name and the rule it violates (`name must be lowercase ASCII letters only`), and the load does not abort other valid rows.
6. **Given** an upstream proxy-group of type `relay` with a member list `[NodeA, NodeB]`, **When** the merge runs, **Then** the merged config contains `<provider>_<original-group-name>` whose member list is `[<provider>_NodeA, <provider>_NodeB]` (every element rewritten).

### User Story 2 - Drop Each Upstream's Trailing Rule So Multiple Sources' Rules Can Coexist (Priority: P2)

Most upstream subscriptions terminate their `rules` block with a catch-all (typically `MATCH,auto` or `MATCH,DIRECT`) that, if preserved verbatim during a multi-upstream merge, would short-circuit everything that comes after it. The operator wants the merge to **drop the final rule** from every upstream's rule list before concatenating, so that all upstreams' meaningful (pre-MATCH) rules can actually match in priority order.

**Why this priority**: Without this, the merged rule list emitted by 001's pipeline is functionally broken whenever ≥2 upstreams contribute rules — the highest-priority upstream's `MATCH` catches everything before any lower-priority upstream's rules ever fire. P2 because P1 is a precondition (rule targets must already be namespaced before the rule list is meaningful), but the value lands the moment ≥2 upstreams contribute rules.

**Independent Test**: Configure one upstream whose final rule is `MATCH,auto` and verify the merged output excludes it; configure two upstreams (each ending with a different MATCH rule) and verify both are dropped, leaving only the meaningful pre-MATCH rules from both (with their targets rewritten per US1) — followed by **exactly one** server-emitted `MATCH,<fallback-target>` rule at the very end. Override `FALLBACK_RULE_TARGET=DIRECT` and verify the server-emitted rule changes accordingly while the rest of the output is byte-identical.

**Acceptance Scenarios**:

1. **Given** an upstream's `rules:` is `[DOMAIN,a.test,Auto, MATCH,auto]`, **When** the merge runs with `FALLBACK_RULE_TARGET` unset, **Then** the merged config contains `DOMAIN,a.test,alpha_Auto`, does NOT contain any rule from this source whose final field equals `auto` in its un-prefixed form (the upstream's trailing rule is gone), AND ends with exactly one server-emitted `MATCH,auto` rule at the very end.
2. **Given** two upstreams each end with a `MATCH,*` rule, **When** the merge runs, **Then** both upstream trailing rules are absent from the merged output, every other rule from both sources is present (with its target rewritten per US1), and exactly one server-emitted `MATCH,<fallback-target>` rule appears at the very end.
3. **Given** an upstream's `rules:` is empty, **When** the merge runs, **Then** dropping the trailing rule is a no-op for that source (recorded in structured logs as `trailing-rule-drop:noop`, not an error). The merged output's final rule is still the server-emitted `MATCH,<fallback-target>`.
4. **Given** the trailing rule is NOT a `MATCH` rule (e.g., the upstream forgot it), **When** the merge runs, **Then** the rule is still dropped per the documented unconditional rule (rationale: deterministic, simple, matches the user's stated intent).
5. **Given** `FALLBACK_RULE_TARGET=DIRECT` is set in the environment, **When** the server starts and the merge runs, **Then** the merged output's final rule is `MATCH,DIRECT` (not `MATCH,auto`), the chosen value is logged at startup, and every other rule in the merged output is byte-identical to the run with `FALLBACK_RULE_TARGET` unset.
6. **Given** every upstream contributes zero rules (all empty after the trailing-rule drop, or all `Disable`d), **When** the merge runs, **Then** the merged output's `rules:` block contains **exactly one** rule — the server-emitted `MATCH,<fallback-target>` — and nothing else.

### User Story 3 - Group Nodes by Region Into ISO 3166-1 Alpha-2 Proxy Groups (Priority: P3)

Each upstream provides node display names that include a country indicator (emoji flag, Chinese country name, or English country name). The operator wants the merged config to expose, on top of the per-provider prefixed groups, a set of region-based proxy-groups (`_region_CN`, `_region_US`, `_region_HK`, …) whose members are the namespaced proxies inferred to be in that country, regardless of which upstream they came from. The leading underscore tags these groups as server-emitted (per the FR-007d convention). This lets the client pick "any HK exit" or "any US exit" without caring about provider.

**Why this priority**: Convenience layer on top of US1+US2. Region groups are deterministic, additive (they don't replace anything from US1), and depend on US1's namespacing being in place. They are not required for correct merging of two providers, hence P3.

**Independent Test**: Provide two upstream subscriptions whose proxies' display names include a recognized country indicator (e.g., one node named `🇭🇰 香港 01`, another named `美国 LA Premium`); fetch the merged subscription; assert the served config contains a `_region_HK` group whose members include the prefixed first node, and a `_region_US` group whose members include the prefixed second node.

**Acceptance Scenarios**:

1. **Given** an upstream `alpha` contributes a proxy whose display name contains `🇭🇰` (the HK regional-indicator emoji pair), **When** the merge runs, **Then** the merged config contains a `_region_HK` group whose member list includes that proxy in its prefixed form (`alpha_<original-name>`).
2. **Given** two upstreams both contribute nodes with `美国` (United States) in their display names, **When** the merge runs, **Then** the merged config contains exactly one `_region_US` group whose members are the namespaced proxies from both upstreams in source-priority order (per 001's FR-005a).
3. **Given** a node's display name contains no recognized country indicator, **When** the merge runs, **Then** the node still appears in the per-provider group(s) it originally belonged to (now prefixed per US1) but is not added to any `_region_*` group.
4. **Given** the same set of upstream payloads, **When** the merge runs twice in succession, **Then** the membership and ordering of every `_region_*` group is byte-identical across the two runs (Constitution Principle II — deterministic transformation).
5. **Given** a node's display name contains both a Chinese country name and a country emoji flag that map to *different* countries, **When** the merge runs, **Then** the documented precedence rule applies (emoji > Chinese > English) and the node is assigned to a single deterministic region.
6. **Given** every upstream's proxies have unrecognized display names (no country indicator anywhere), **When** the merge runs, **Then** the merged config contains zero `_region_*` groups (no empty-group placeholders are emitted).
7. **Given** the operator declares an own-proxy `my-canada-1` and an own-group `my-canada-pool` whose `proxies:` list is `[my-canada-1, DIRECT]`, **When** the merge runs, **Then** the merged config contains a proxy `_my-canada-1` and a group `_my-canada-pool` whose `proxies:` list is `[_my-canada-1, DIRECT]` (own-proxy reference rewritten; built-in `DIRECT` left unchanged).
8. **Given** the operator declares an own-proxy whose display name is `🇨🇦 my-canada-1` (carries a recognized country emoji), **When** the merge runs, **Then** the proxy is renamed to `_🇨🇦 my-canada-1` and is **NOT** added to a `_region_CA` group; if no upstream contributes a CA-classified proxy, the merged config contains no `_region_CA` group at all (own-proxies are excluded from region inference per FR-012).

### Edge Cases

- **Subscription `name` is empty** / contains uppercase / contains digits / contains underscore / contains punctuation / contains non-ASCII letters: skipped at load time with a stdout warning naming the offending field; does NOT abort the loading of the rest of the CSV.
- **Two subscriptions whose `name` differs only in case** (e.g., `Alpha` vs `alpha`): the uppercase-bearing one fails FR-001's rule and is skipped. (001's FR-001a duplicate-`name` loud-failure rule still applies if two rows pass FR-001 and produce identical lowercase prefixes — duplicates remain a hard load-time error.)
- **An upstream proxy's display name contains an underscore**: prefixing is unaffected; the prefixed form is `<provider>_<original-with-underscores>`. The underscore in the original is irrelevant — only the **provider name** is constrained by FR-001.
- **An upstream proxy-group references a built-in target** (`DIRECT`, `REJECT`, `REJECT-DROP`, `PASS`) inside its `proxies:` list: the reference is left unchanged.
- **An upstream rule's target is a built-in** (`DIRECT`, `REJECT`, `REJECT-DROP`, `PASS`): the target is left unchanged.
- **An upstream rule's target is a name not declared in any of that source's groups or proxies** (rare but legal in raw upstreams): the target is still rewritten with that source's prefix per FR-006, producing a possibly-dangling reference. The dangling reference is recorded in logs but not an error (matches the pre-existing tolerant behavior of Mihomo clients).
- **A `_region_<CC>` group ends up with zero members** across all upstreams: the group is omitted from the merged output entirely (no empty groups).
- **A node's display name contains an emoji flag for a country not present in the maintained translation table**: the node is left unassigned to any `_region_*` group; a structured log records the unmapped indicator once per distinct value, so the operator can decide whether to extend the table.
- **An upstream contributes 0 rules** (empty list, or only the trailing rule that gets dropped): the source contributes 0 rules to the merged output; not an error.
- **Region-group naming collides with an upstream's existing group name** (an upstream literally named a group `_region_CN` or `region_CN`): the upstream's prefixed form (`<provider>_region_CN` or `<provider>__region_CN`) starts with a lowercase ASCII letter and is therefore distinct from the server-emitted `_region_CN` (which starts with `_`), so no collision.
- **An own-proxy's original name already starts with an underscore** (e.g., `_legacy-exit`): the prefix rule applies literally — the merged form becomes `__legacy-exit` (two leading underscores). The operator may rename to remove the legacy underscore if they prefer a single-underscore form, but the server does not coerce.
- **An own-group's `proxies:` member list references an upstream proxy by its un-prefixed name** (e.g., `my-group: { proxies: [Node1] }` where `Node1` is contributed by upstream `alpha`): the server attempts to rewrite to the upstream-prefixed form (`alpha_Node1`); if the source name cannot be unambiguously inferred from the member-list context, the reference is left unchanged and a structured log records the dangling reference.
- **A node's display name contains a country indicator inside a substring that is NOT meant as a country marker** (e.g., a node named `中国电信 backup` where `中国` is part of an ISP name): the table-based match still triggers and the node is classified as `CN`. This is an accepted false-positive trade-off; operators who care can rename their nodes upstream or extend the table with negative keywords (out of scope for this feature).

## Requirements *(mandatory)*

### Functional Requirements

#### Subscription Name Validation

- **FR-001**: The subscriptions CSV `name` field (defined by 001's FR-001a) MUST match the regular expression `^[a-z]+$` — one-or-more ASCII lowercase letters, with no digits, no underscores, no punctuation, no whitespace, and no non-ASCII letters. The server MUST validate this rule at config load time and at every config reload.
- **FR-002**: When a row's `name` fails FR-001's rule, the server MUST: (a) emit a warning to stdout naming the offending value and the rule it violated (`name must match ^[a-z]+$`); (b) exclude the row from the merged output (no proxies, groups, or rules from that row contribute to the served config); (c) continue loading the remaining rows. The exclusion MUST be recorded in startup/reload logs as `name-format-violation`, distinct from the `Disable` exclusion of 001's FR-001a so an operator scanning logs can tell them apart.
- **FR-003**: FR-001 strengthens — but does not invalidate — 001's FR-001a's loose `name` constraint. An existing CSV containing rows with non-lowercase names will see those rows excluded once this feature ships, with a stdout warning per row. The migration step is operator-side: rename such rows to lowercase ASCII letters.

#### Provider Namespacing of Proxies, Groups, and Rule Targets

- **FR-004**: For every upstream proxy that survives loading and merging, the server MUST rewrite the proxy's display name to `<provider>_<original-name>`, where `<provider>` is the source's CSV `name` (already validated to match `^[a-z]+$` per FR-001). The rewriting is performed in the transformation core (Constitution Principle I) before the proxy is emitted in the merged output.
- **FR-005**: For every upstream proxy-group that survives loading, the server MUST: (a) rewrite the group's `name` to `<provider>_<original-group-name>`; (b) rewrite every name appearing in any list-of-names attribute the group exposes — including but not limited to `proxies` (for `select` / `url-test` / `fallback` / `load-balance` types) and any `relay` exit list — to its prefixed form per FR-004. Built-in identifiers (`DIRECT`, `REJECT`, `REJECT-DROP`, `PASS`) inside such lists MUST be left unchanged.
- **FR-006**: For every upstream rule, the server MUST rewrite the rule's **target field** (the trailing token, e.g., the `Auto` in `DOMAIN,a.test,Auto`) to `<provider>_<target>`, EXCEPT when the target is a built-in identifier (`DIRECT`, `REJECT`, `REJECT-DROP`, `PASS`), which MUST be left unchanged. Other rule fields (matcher type, matcher value, optional `no-resolve` modifier) MUST NOT be modified.
- **FR-007**: The provider-prefix namespacing of FR-004 / FR-005 / FR-006 supersedes 001's per-source-suffix collision strategy in FR-002: cross-source name collisions are now structurally impossible because every name carries its source's distinct lowercase-alphabets prefix. The collision-resolution log line from 001's FR-002 is now reserved for genuine **intra-source** duplicates (which remain a loud-failure condition).

#### Own-Proxy / Own-Group Underscore Namespacing

- **FR-007a**: For every proxy declared in the own-proxies file (001's FR-006), the server MUST rewrite the proxy's display name to `_<original-name>` (a single leading underscore followed by the original name verbatim).
- **FR-007b**: For every proxy-group declared in the own-proxies file (001's FR-007), the server MUST: (a) rewrite the group's `name` to `_<original-group-name>`; (b) rewrite every name appearing in any list-of-names attribute the group exposes (`proxies` for `select` / `url-test` / `fallback` / `load-balance`; `relay` exit list; etc.) such that any reference to an own-proxy or another own-group becomes its underscore-prefixed form, EXCEPT that built-in identifiers (`DIRECT`, `REJECT`, `REJECT-DROP`, `PASS`) MUST be left unchanged. References to upstream proxies/groups by name from inside an own-group's member list are out of scope (own-groups are not expected to reference upstream-only entities; if such a reference exists in operator-supplied YAML, it is rewritten to its `<provider>_<original>` upstream form per FR-005's lookup rules — the operator is responsible for declaring the correct upstream provider name).
- **FR-007c**: Cross-namespace name collisions (an own-proxy named `Foo` and an upstream proxy named `Foo` from source `alpha`) are structurally impossible after FR-004 + FR-007a: the upstream form is `alpha_Foo`, the own form is `_Foo`, so the merged output contains both with distinct names. The 001 FR-008 own-proxy-precedence-on-collision rule is preserved as a defense-in-depth invariant for genuine intra-namespace duplicates only.
- **FR-007d**: The leading-underscore namespacing convention establishes three disjoint name-shape classes in the merged output, which together make every name's origin unambiguous from its first character: (1) **upstream-sourced** names start with a lowercase ASCII letter (the source's CSV `name` per FR-001 `^[a-z]+$`), e.g., `alpha_Node1`; (2) **operator/server-emitted** names start with `_`, e.g., `_my-canada-exit`, `_region_HK`; (3) **built-in identifiers** are uppercase, e.g., `DIRECT`, `REJECT`. Other rule fields and built-in matcher types (DOMAIN-SUFFIX, IP-CIDR, etc.) are out of scope of the name-shape rule.

#### Trailing-Rule Drop

- **FR-008**: For every upstream that contributes a non-empty `rules:` block, the server MUST drop the **final** entry of that source's rule list **before** rule prefixing (FR-006) and **before** concatenation into the merged output. The drop is **unconditional** — it applies whether or not the trailing rule is `MATCH,*`.
- **FR-009**: When a source's `rules:` is empty (or becomes empty after merging upstream cache state), FR-008 is a no-op for that source; this MUST be recorded in structured logs as `trailing-rule-drop:noop` and MUST NOT raise an error.
- **FR-010**: After every source's trailing rule is dropped per FR-008 and before the merged config is served, the server MUST append exactly **one** server-emitted final fallback rule of the form `MATCH,<target>` to the end of the merged `rules:` block. The default `<target>` is the literal string `auto`. The default MUST be overridable at deployment time via the environment variable `FALLBACK_RULE_TARGET` (consistent with the existing `LOG_LEVEL`, `PROXIES_GROUP_NAME`, `UPSTREAM_USER_AGENT` env-var convention from 001's `internal/config/server.go`). When `FALLBACK_RULE_TARGET` is set to a non-empty value, that value is used as the rule target verbatim — it is **not** subject to the per-provider prefixing of FR-006 (the server-emitted fallback is, by definition, not from any provider) and it is **not** validated against the FR-001 lowercase-alphabets rule (FR-001 governs CSV `name` values, not rule targets — built-in identifiers like `DIRECT`/`REJECT` and any operator-defined target groups are out of scope for that rule). When `FALLBACK_RULE_TARGET` is unset or empty, the default literal `auto` is used. The chosen value MUST be recorded in startup logs.
- **FR-010a**: The server-emitted fallback rule MUST appear **exactly once** in the merged output, **after** all upstream-contributed (and prefixed) rules, and **regardless of whether** any upstream contributed any rules at all (i.e., the server-emitted fallback is unconditional — even an empty merged rule list ends with it).

#### Region (ISO 3166-1 Alpha-2) Grouping

- **FR-011**: The server MUST maintain an in-process **country-indicator translation table** mapping human-readable country indicators to ISO 3166-1 alpha-2 codes. The table MUST cover, at minimum: (a) Chinese country/region names commonly emitted by Chinese providers (e.g., 中国, 美国, 日本, 香港, 台湾, 新加坡, 韩国, 英国, 德国, 法国, 加拿大, 澳大利亚, 俄罗斯, 印度, 越南, 泰国, 马来西亚, 菲律宾, 印度尼西亚, 巴西, …); (b) common English country/region names; (c) every emoji regional-indicator pair (which is a pure 2-codepoint → 2-letter ASCII transform and therefore needs no table entries beyond a runtime decoder). The table MUST be defined in code so it is reviewable, version-controlled, and deterministic (Constitution Principle II).
- **FR-012**: For every **upstream-sourced** merged proxy (i.e., every namespaced proxy from FR-004), the server MUST attempt to infer a country code by scanning the proxy's **original display name** (the value before FR-004's prefixing) for, in this precedence order: (1) a country emoji flag — highest precedence; (2) a Chinese country name from FR-011's table — next; (3) an English country name from FR-011's table — last. The first hit determines the country; subsequent hits in the same name are ignored. **Own-proxies (FR-007a) are explicitly out of scope for country inference** — they are never scanned and never classified into a region.
- **FR-013**: For every distinct country code inferred under FR-012, the server MUST emit one new proxy-group named `_region_<CC>` (a single leading underscore, then the literal `region_`, then `<CC>` — the alpha-2 code, **uppercase**) of type `select`, whose member list is every **upstream-sourced** namespaced proxy inferred to be in that country (own-proxies are excluded per FR-012). The member ordering MUST be deterministic: by source priority (001's FR-005a, descending), and within a source by the proxy's original order of appearance. Region groups whose membership would be empty MUST be omitted from the merged output. The `_region_` prefix follows the leading-underscore convention from FR-007d (server-emitted names start with `_`).
- **FR-014**: An upstream-sourced proxy whose display name contains no recognized country indicator MUST NOT be added to any `_region_*` group; it remains in the per-provider prefixed group(s) it already belongs to per FR-005 and in the always-present `Proxies` global group from 001's FR-009a. Own-proxies (excluded from region inference per FR-012) similarly remain only in their underscore-prefixed own-groups (FR-007b) and in `Proxies`. The "unmapped" condition for upstream proxies MUST be recorded once per distinct unmapped name fragment in structured logs (so the operator can decide whether to extend FR-011's table) — repeated occurrences within a single merge SHOULD be deduplicated to avoid log spam.
- **FR-015**: Region grouping is purely additive — the per-provider prefixed groups from FR-005 and the underscore-prefixed own-groups from FR-007b remain in the merged output unchanged. The newly emitted `_region_*` groups MUST also be appended as additional members of the always-present `Proxies` selectable group from 001's FR-009a, so they are pickable from the client UI alongside individual nodes.
- **FR-016**: Region grouping MUST be deterministic (Constitution Principle II): the inferred country for each node is a pure function of (the proxy's original display name, FR-011's translation table). The set of emitted region groups, their member lists, and their order in the served config MUST be byte-identical across two runs over identical inputs.

### Key Entities

- **Subscription Source / Provider**: identified by a CSV `name` matching `^[a-z]+$`. Used as the always-present prefix for every proxy, every proxy-group, and every rule target contributed by that source.
- **Country Code**: an ISO 3166-1 alpha-2 string (e.g., `CN`, `US`, `HK`). Inferred from a node's original display name via the FR-011 translation table.
- **Country-Indicator Translation Table**: an in-process mapping from human-readable indicators (Chinese names, English names) to country codes, plus a runtime decoder for emoji regional-indicator pairs. Owned by this feature; extensible via patches.
- **Region Proxy Group**: a derived proxy-group named `_region_<CC>` (single leading underscore, then `region_`, then uppercase CC) whose members are every namespaced proxy inferred to be in `<CC>`. Type `select`. Emitted only when its membership is non-empty. Naming follows the FR-007d server-emitted convention (leading `_`).
- **Own-Proxy / Own-Group Namespace**: identified by a leading single underscore (`_<original-name>`). Distinguishes operator-declared entities (from the own-proxies file) from upstream-contributed entities (which start with a lowercase ASCII letter per FR-001) and from built-in identifiers (which are uppercase).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After this feature ships, 100% of proxies, proxy-groups, and rule targets in the merged output that came from a configured source carry that source's lowercase-alphabets prefix. Built-in identifiers (`DIRECT`, `REJECT`, `REJECT-DROP`, `PASS`) are never prefixed.
- **SC-002**: After this feature ships, no merged subscription served by the production binary contains two proxies, two proxy-groups, or two rule targets with identical names sourced from different upstreams (cross-source collisions are structurally impossible).
- **SC-003**: A subscriptions CSV that includes one row whose `name` violates `^[a-z]+$` produces (a) a stdout warning naming that row and citing the rule, (b) a merged output whose proxy/group/rule lists contain zero contributions from that row, and (c) zero impact on the contributions of conforming rows.
- **SC-004**: A merged subscription built from two or more sources, each ending with a `MATCH,<target>` rule, contains zero upstream-attributable `MATCH` rules, AND every pre-trailing rule from every source appears in the merged output (with its target rewritten per FR-006), AND ends with exactly one server-emitted `MATCH,<fallback-target>` whose target equals `auto` by default (or the value of `FALLBACK_RULE_TARGET` when set).
- **SC-005**: A node whose original display name contains a recognized country indicator (emoji flag, Chinese country name in the table, or English country name in the table) is assigned to exactly one `_region_<CC>` group; given identical inputs, that assignment is byte-identical across two independent merge runs.
- **SC-006**: Adding a third subscription source named `<lowercase>` to the CSV requires no further configuration changes to: (a) namespace that source's contributions; (b) drop its trailing rule; or (c) classify its nodes into existing region groups. All three behaviors emerge automatically from the validated `name` and the FR-011 translation table.
